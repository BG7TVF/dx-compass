# 设备页面改造为画布编辑器 · 实施方案

> 依据：`docs/device-integration-review.md` 已定死的设备模型与语义；本次只换交互层，不改后端语义。
> 目标：设备页面的交互范式对齐 Node-RED 编辑器——左侧面板、中间画布、连线表达父子、选中后编辑属性。

---

## 0. 对「拖拽放置」的理解（需要确认的歧义）

采用：**从左侧面板拖出即创建一个新的设备实例**（类似 Node-RED 从面板拖出节点），不是「已有设备只调整位置」。

但与 Node-RED 一致，实例先以**草稿态**存在于画布，用户填完属性点「保存」才写入 SQLite。原因：

- 天线必须填写波段（已定死的校验），拖出时没有合理默认值，不能强行落库；
- Node-RED 本身也是拖出 → 编辑 → Deploy 才生效，草稿态更贴近参照物；
- 草稿在画布上有明显虚线样式；未保存就切换选择时提示「有未保存的更改」，可放弃或继续编辑。

如果实际意图是「设备已存在，拖拽只调整排布」，改动范围会缩小为：仅新增 `device_layout` 存取 + 画布渲染，不涉及拖出创建、草稿态和属性面板改造。当前方案按「拖出创建」实现，同时保留「+ 添加设备」按钮作为等价入口。

## 2. 目标交互形态

```
┌ 工具栏：标题 / 席位选择 / 统计 / 刷新 / 添加设备 ────────────────┐
├──────────┬──────────────────────────────┬────────────────────┤
│ 设备面板  │           画布                │      检查器         │
│ 按类型分组 │  节点 = 设备卡片              │  属性表单           │
│ 拖出即创建 │  连线 = parent_id 父子关系     │  控制（旋转/切换/塔）│
│ TX 源状态 │  拖动改位置（拖动结束落库）    │                    │
├──────────┴──────────────────────────────┴────────────────────┤
│ 底部可折叠：席位→天线归属三态表 / TX 上报源表（只读监控保留）        │
└───────────────────────────────────────────────────────────────┘
```

- 画布是可缩放、可平移的工作区（滚轮缩放、空白处拖动平移），节点绝对定位；连线用 SVG 三次贝塞尔。
- 支持框选/多选后整体拖动，位置随设备保存；工具栏「自适应」按当前节点重新取景。
- 节点卡片展示：名称、类型、波段、在线点、关键运行态（旋转器角度/塔二态/天线三色 chip）。
- 画布顶部保留「未接入发射状态源」提示（沿用现有 TX 面板语义）。
- 右侧检查器分三块：属性、控制、运行态摘要；席位与 TX 表移到底部折叠区，避免挤压画布。

## 3. 数据模型

### 3.1 位置存放：新增 `device_layout` 表（SQLite）

```sql
CREATE TABLE IF NOT EXISTS device_layout (
    device_id TEXT PRIMARY KEY,
    x INTEGER NOT NULL DEFAULT 0,
    y INTEGER NOT NULL DEFAULT 0,
    updated_ts TEXT NOT NULL
);
```

理由：

1. 评审已确认 settings 不支持对象数组且会广播给大屏，不适合存布局；
2. 布局与设备是 1:1 的纯展示数据，独立表可避免污染 `devices` 的功能字段，也避免在 `config_json`（协议配置）里混入 UI 数据；
3. 设备删除时同步删除布局行，不留孤儿；
4. 建表即可幂等迁移，不需要 `ALTER TABLE`，对旧库零风险。

写入用 `INSERT OR REPLACE`（SQLite 全版本可用，避免依赖 UPSERT 语法）。所有 SQL 仍在 `lib/storage/devices-sql.js`。

### 3.2 快照输出

- `toDevice` 读取 `layout_x/layout_y` → `layout: {x, y} | null`。
- `snapshotQuery` 左连接 `device_layout`，列名 `layout_x/layout_y`。
- `snapshot()` 对没有布局行的设备套用**确定性自动布局**（`lib/devices/layout.js`），输出 `device.layout` 始终可用；附带 `layout_saved: boolean` 表示是否已落库。
- 设备配置保存（save）不触碰布局；只有 `action: "layout"` 写位置。

### 3.3 自动布局算法（迁移用）

1. 以 `parent_id` 建森林，根按名称排序；
2. 深度决定列 `x = 80 + depth * 280`；
3. 同层按先序遍历顺序决定行 `y = 80 + index * 120`；
4. 环/孤儿兜底：不可达节点按 id 排序放最后一列，保证一定渲染得出来。

已有设备第一次打开页面即按此布局呈现，父子关系直接画成连线；用户拖动后写库，之后以库为准。

## 4. 接口变更

沿用现有入口，不新增路由：

1. `GET /api/devices`：新增每台设备的 `layout: {x, y}` 与 `layout_saved`，其余字段不变。
2. `POST /api/devices` 新增 `action: "layout"`：

```json
{"action": "layout", "layouts": [{"id": "tower-1", "x": 120, "y": 80}]}
```

- 校验：`layouts` 为数组；`id` 必须存在；`x/y` 为 0–10000 的整数；单次最多 200 条；
- 返回 `{ok:true, saved:[...]}`，并广播 `{type:"devices", action:"layout"}`；
- 未知设备返回 404 `unknown-device`，非法坐标返回 400 `invalid-layout`；
- 删除设备时额外产出 `DELETE FROM device_layout WHERE device_id = ...`。

---

## 5. 连线规则（强制既有约束）

- 拖拽从节点右侧输出端口到目标节点左侧输入端口 = 设置 `parent_id = 源节点`。
- 客户端即时校验：不能连自己、不能连后代（成环）→ 松手即回弹并 toast 提示「会形成环」。
- 服务端仍以 `normalizeDevice` 的 `cycle/unknown-parent` 校验兜底，客户端提示不替代服务端。
- 单父：连线成功后旧连线自动消失（`parent_id` 被覆盖），不产生多条父线。
- 断开连线：鼠标悬停连线中点出现「×」，点击后 `parent_id = null`。
- 删除设备沿用「有子节点禁止删除」，错误提示不变；删除成功后画布节点与关联布局一起消失。
- 不做类型白名单：任何节点都可作为连线两端。

## 6. 迁移方案

1. **数据**：只新增空表，旧库数据零改动；已配置设备、口令、租约、审计全部原样保留。
2. **位置**：无布局行的设备用第 3.3 节算法自动摆放，父子关系按 `parent_id` 转连线。
3. **回滚**：新表可忽略；页面回退旧版仍能正常工作（旧版不读 `layout`）。

## 11. 关键复核：`parent_id` 是否足以表达真实射频链路（已裁决：按方案 B 实施）

前提修正：画布上的一切代表真实射频系统的物理连接，是硬件拓扑的唯一来源。据此复核现有模型：

**现状结论（只有机械/控制挂载，没有射频链路）**

- `parent_id` 只有一条边，语义是挂载：塔 → 旋转器 → 天线。`device.type` 只是类型标签，`config.channels` 只是继电器通道号，不是拓扑。
- 归属判定 `ownership.project` 是「席位当前波段 → 所有带该波段的天线」，不检查信号路径；因此它是**波段集合**，不是**路由可达**。
- TX 互锁 `commands.execute` 只看全局 TX 源状态，不区分该设备是否在发射链路上；因此是**全系统互锁**，不是**按链路互锁**。
- `model.resolveRotator` 沿 `parent_id` 向上找最近的旋转器，暗含「旋转器是机械祖先」。这正是把机械挂载与信号控制压在一条边上的表现。

**方案 A：只保留挂载关系（当前代码实现）**

- 数据：一个 `parent_id`，无新增表。
- 渲染：单色连线，方向从父到子。
- 判定：归属仍按波段；互锁仍全局；旋转器仍沿祖先解析。
- 优点：简单、与现有测试和语义一致、零迁移。
- 缺点：无法回答「这台电台经哪台切换器到哪副天线」，多席位多路径时会误判归属与互锁范围。

**方案 B：挂载 + 独立 RF 链路**

- 数据：`parent_id` 继续作为机械挂载；新增 RF 端点与连线（例如 `device_ports(device_id, port_id, direction, role)` + `rf_links(from_device, from_port, to_device, to_port)`）。RF 图允许端口级多入多出，但仍需端口互斥规则。
- 渲染：机械挂载用现有连线；RF 链路用第二种颜色与端口（电台/功放/切换器/矩阵 OUT/天线），可与父线并存。
- 判定：归属改为沿 RF 链路从席位电台向下可达；互锁只作用于当前 RF 路径；旋转器仍按机械祖先解析，控制与信号解耦。
- 影响：`ownership`、`commands` 互锁、快照 DTO、迁移（旧设备没有端口，需要默认端口或标记「未接线」）都要改，测试面显著扩大。

**当前处理：方案 B 已落地。** `parent_id` 继续只表示机械/控制挂载；`rf_links` 保存端口级射频连线，端口方向能力与 BFS 判定见第 13 节。画布已渲染底部 RF 端口、橙色 RF 连线与端口来源；`ownership`、TX 互锁、快照 DTO 均已切到 RF 链路（无电台/无连线时回退到 `band-fallback`）。本节保留为决策依据，不再表示「未改结构」。

### 11.1 九种可拖拽类型对 RF 链路判断的影响

面板最终为十一种：电台、驻波表、BPF、功放、天线、塔、旋转器、切换器、矩阵切换器、合路器、串口服务器。其中**电台 → 驻波表 → BPF → 功放 → 天线**本身是一条射频链路；塔与旋转器是机械支撑；切换器（1×n）与矩阵切换器（n×n）是射频路由，且两者是**不同类型**——1×n 不套用多席位共享占用判定、不显示黄灯，n×n 才按席位投影红/黄/绿。这进一步支持方案 B 的必要性：

- 只靠 `parent_id` 时，机械支撑与射频顺序共用一条边，无法区分「塔 → 旋转器 → 天线」和「电台 → 功放 → 天线」这两类语义完全不同的关系；
- 归属需要知道「席位电台 → 经过哪些器件 → 到达哪副天线」，单靠天线波段无法表达驻波表/BPF/功放的旁路与选择；
- 互锁范围应覆盖 TX 路径上的器件，而不是全系统一刀切；
- 方案 B 中 `parent_id` 继续只表示机械支撑（塔/旋转器），RF 链路用端口连线表达，两套边可以同时存在且互不干扰。

### 11.2 现有七种之外的设备类型盘点（不删除，待用户决定）

| 类型 | 当前用途 | 代码引用 | 移除/保留影响 |
|---|---|---|---|
| `matrix` | n×n 矩阵 OUT，Phase 4 的 `select` 写操作；`exclusive=false` 时归属可出现黄灯 | `commands.js` 的 `COMMAND_TYPES`、`relay` 下发、`ownership`、测试 | 移除会破坏矩阵切换与 Phase 4 能力；保留则需在 RF 方案里把它建模为多端口路由节点 |
| `switch` | 1×n 天线切换器，Phase 4 的 `select` 写操作；`exclusive=true` 时无黄灯 | 同上 | 同上；1×n 在 RF 图里是单入多出选择器 |
| `other` | 通用兜底类型，旧数据或临时节点 | 类型校验、测试、i18n | 可保留为兼容类型，不出现在面板 |
| TX 上报源 | 独立的 `tx_sources` 表，不是设备；提供二元发射状态、优先级与超时降级 | `tx.js`、`service.ingestTx`、`commands` 互锁、监控面板 | 它不是可拖拽设备，不能塞进设备树；若采用方案 B，可考虑把 TX 源绑定到「电台」节点，但仍是独立表与独立入口 |

**结论**：矩阵与切换器保留在后端、检查器与画布中，并已按第 13 节建模为多端口路由节点；TX 源保持独立表，通过 `device_id` 绑定到设备实例。1×n 与 n×n 的端口语义已落地：切换器 `in` + `antN`，矩阵 `inN` + `outM`。

> 后续用户已裁决按方案 B 执行。面板最终为十一种：电台、驻波表、BPF、功放、天线、塔、旋转器、切换器、矩阵切换器、合路器、串口服务器；功分器已由用户明确移除，阵列相关设计一并作废。RF 数据模型与判定规则见第 13 节，11.2 中「不出现在面板」的临时结论作废。

## 13. 方案 B：RF 链路数据模型与判定规则（已裁决实施）

### 13.1 两条独立的关系边

| 边 | 存储 | 语义 | 画布渲染 |
|---|---|---|---|
| 机械/控制挂载 | `devices.parent_id` | 塔 → 旋转器 → 天线等支撑与控制关系；单父、无环 | 现有实线，父在左、子在右 |
| 射频链路 | 新表 `rf_links` | 端口到端口的同轴连接，不限制单父，允许分叉/汇合/并行 | 第二种颜色的连线，端点画在设备底部的 RF 端口上 |

删除设备时同时删除 `parent_id` 子关系校验之外的所有 `rf_links` 引用行。

### 13.2 RF 链路表（无向连接 + 端口方向能力）

```sql
CREATE TABLE IF NOT EXISTS rf_links (
    link_id    TEXT PRIMARY KEY,
    a_device   TEXT NOT NULL,
    a_port     TEXT NOT NULL,
    b_device   TEXT NOT NULL,
    b_port     TEXT NOT NULL,
    created_ts TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS rf_links_pair ON rf_links (
    a_device, a_port, b_device, b_port
);
```

**方向性选择：无向连线 + 每个端口声明方向能力**，而不是为收发各存一条有向边。

- 物理上是一根同轴线，存两条边会产生不一致风险；
- 端口能力 `dir ∈ {in, out, bidir}` 表达器件约束：功放/驻波表/BPF 为 `in` + `out`，电台 `ant`、天线 `feed` 为 `bidir`；切换器为 `common`(in) + `outN`(out)，矩阵为 `inN` + `outM`，合路器为 `in:<band>` + `out`。
- 本阶段只实现 TX 方向判定：只允许从 `out|bidir` 端口离开、进入 `in|bidir` 端口，功放不会倒灌。RX 反向遍历未实现，也不为「接收分路」保留特殊路径；功分器移除后没有该场景。

端口不单独建表，由类型默认值 + 实例配置生成，`rf_links` 只用 `(device_id, port_key)` 引用：

- `config.port_count` / `config.in_count` / `config.out_count` 在检查器里可配，默认值：
  - 电台 `ant`×1（bidir）；驻波表/BPF/功放 `in`+`out`；天线 `feed`×1（bidir）
  - 切换器（1×n）`common` + `out1..outN`（默认 2）
  - 矩阵（n×n）`in1..inN` + `out1..outM`（默认 2×4）
  - 合路器：**in 口由所选波段派生，一个波段一个 in 口**（`in:10m`、`in:15m`…），没有独立的输入数量字段；另加单端口 `out`。波段集合为空时拒绝保存（`combiner-band-required`）。
  - 塔/旋转器没有 RF 端口
- 高级用户可用 `config.ports`（JSON 数组，`[{key,dir,band?}]`）覆盖默认端口；校验端口 key 唯一、方向合法、band 合法。
- 旧设备不写端口数据：每次读取时按类型默认值即时派生，用户显式配置端口后才落库。

### 13.3 席位 → 电台的显式绑定（缺口 1 的处理）

新增 `devices.seat TEXT` 列（可空，幂等 `ALTER TABLE`），仅 `type='radio'` 有意义，检查器里编辑「所属席位」。理由：RF 可达必须从席位电台出发；用名称/波段猜测会产生不可解释的归属。一个席位可绑定多台电台（SO2R），遍历时取并集。

旧部署没有电台节点时，`ownership` 回退到现有「波段 → 天线」逻辑，并在输出标记 `source: "band-fallback"`，保证升级后立即可用；一旦配置了电台与 RF 链路就自动切换到链路判定。

### 13.4 可达判定（图遍历，不复用 parent 链）

对每个在线席位、每个当前波段：

1. 取该席位绑定的所有电台作为起点；无绑定则走 13.3 的回退。
2. 以 `(device, port)` 为节点做 BFS，`visited` 防重复；该防重只防止图遍历重复访问与环，不承担冲突仲裁。切换器/矩阵按运行态里的 `ports[入口] = 出口` 跟随当前选择；选择未知且输出多于一个时不假装导通。
3. 端口方向能力按遍历方向过滤（见 13.2）。
4. **波段可行性**：进入某个设备时，如果该设备 `bands` 非空且不包含当前波段，则该分支剪掉。**合路器是特例**：进入端口本身带 `band`，必须与当前波段精确匹配（`in:20m` 只接受 20m），匹配后从唯一 `out` 离开；其他设备仍用设备级检查。
5. 终点为 `type='antenna'` 的设备即该席位当前波段可用天线；同时记录路径（用于 OP 展示）。代价是每个 `(席位, 波段)` 一次 `O(V+E)`，设备数量在几十台量级，2 秒轮询完全够用，不需要预计算缓存。

旋转器解析**不参与** RF 遍历：仍沿 `parent_id` 机械链找最近祖先，与射频可达互不影响。

### 13.5 归属语义与配置校验（已按物理事实简化）

物理前提：一副天线正常只接在一个输出端口上；两个源同时接到同一副天线属于要避免的故障配置，不作为正常模型处理。

归属只有两层：

1. **某席位当前可达的天线集合**：BFS 从席位绑定的电台出发。同一席位可绑定多台电台（SO2R），取并集；单台电台经切换器/矩阵的选择性导通只能落到当前选中的那一路，不产生并行路径，不做仲裁。
2. **当前被谁占用**：在可达集合内按现有红/黄/绿规则投影；`exclusive=true`（1×n）保持既有规则，`exclusive=false`（n×n）沿用既有共享占用。

因此删除 conflict / contenders 分支，不保留「以防万一」的运行时仲裁。BFS 的 `visited` 防重继续保留，它只防止图遍历重复访问与环，不承担冲突判定。

**防御性校验**：如果数据里出现同一副天线被多个上游 RF 连线连接，判定为**配置错误**，在画布与接口校验中提示「这副天线接了多个上游」，由用户修正；运行时仍按 BFS 正常计算，不做仲裁、不静默择一。

### 13.6 TX 互锁范围

- 互锁只作用于**带 RF 端口且位于某条 TX 可达路径上的设备**的天线切换动作（`select`）；塔/旋转器与未接线的设备不受影响。
- 发射状态仍以 TX 源为准，`is_transmitting` 之类推断值不参与。
- 源未接入或中断时互锁不启用、正常放行（既有语义不变）。
- **TX 源绑定设备实例**：`tx_sources.device_id` 指向具体设备（例如某台功放/驻波表），不是席位。源上报发射中时，从该设备沿 RF 链路双向反查同一通路，得到需要锁定的设备与端口；`select` 的入口端口若在这条通路上则返回 423。矩阵按当前选择精确到输入口，另一个输入口的切换不受影响。
- 未绑定设备的旧源保持升级前的全局互锁语义；这样升级不会让已有部署失去保护。

### 13.7 渲染与交互

- 节点底部增加 RF 端口（小方块，按 `in/out/bidir` 显示箭头方向），机械端口仍在左右。
- 从 RF 端口拖到另一个 RF 端口创建 `rf_link`；同一对端口不重复，反向视为同一条。
- RF 连线用第二种颜色；点击连线可删除。机械连线与 RF 连线互不影响。
- 检查器增加：`所属席位`（仅电台）、端口数量（切换器/矩阵）、`bands`（BPF、合路器必填；合路器同时就是 in 口的定义）、TX 源绑定设备。
- 归属面板展示可达路径与来源（`rf` / `band-fallback`）；配置校验提示「同一副天线接了多个上游」「合路器下游天线波段未覆盖」。

### 13.8 测试项

1. `rf_links` 幂等建表、增删、反向去重、删除设备清理、端口变更清理失效连线。
2. 端口默认值按类型生成；数量配置生效；合路器 in 口按波段派生；非法端口拒绝。
3. TX 方向遍历：功放不可倒灌；切换器/矩阵按当前选择导通，未选择时不假装导通。
4. 波段可行性：BPF 只放行配置波段；路径上任意设备缺该波段即不可达；合路器按端口波段精确匹配。
5. 切换器/矩阵选择性：选中哪一路就只到哪一副天线；矩阵一个输入口的切换不影响另一个输入口。
6. 配置校验：同一副天线被多个上游连接、合路器波段未被天线覆盖、孤立连线都给出提示；运行时不仲裁。
7. 回退：无电台/无 RF 链路时 ownership 与旧逻辑一致，标记 `band-fallback`。
8. 互锁：只锁 TX 路径上的 select；塔/旋转器不受影响；未绑定设备的旧源保持全局互锁。
9. 机械挂载与 RF 链路互不干扰；旋转器解析保持原结果。

> 实现状态：后端数据模型与判定逻辑已落地（`rf_links`、`devices.seat`、`tx_sources.device_id`、端口派生、BFS、配置校验、按路径互锁）；画布已渲染底部 RF 端口与橙色 RF 连线，支持拖拽连线、点击断开、合路器波段派生与告警显示；OP 设备控制已改读设备表与运行态，`peripherals.mjs` 与 `op*Configured` 设置项已移除。真实浏览器验证 23/23 通过，截图见 `.screenshots/rf-verify/`。

## 12. 关键复核：OP 视图的设备控制必须收敛到设备表（已实施）

**现状：OP 侧确实存在第二套设备定义。**

| 位置 | 现状 | 职责 |
|---|---|---|
| `public/js/op/peripherals.mjs` → `deviceDefinitions(settings)` | 由 `opAntennaSwitchConfigured` / `opTowerConfigured` / `opRotatorConfigured` 三个开关 + `op*Name` 生成设备卡片 | 前端本地设备清单 |
| `createPeripheralHub()` | 驱动注册表，`setBearing` / `setDirection` / `selectAntenna` 三个动作 | 独立驱动契约 |
| `op-page.mjs` → `renderBottom` / `deviceCard` / `renderAddMenu` / `configureDevice` | 从 settings 渲染卡片；增删设备直接改 settings 并保存 | 第二套配置入口 |
| `handleMapBearing` | 只把方位发给 hub，未调用 `/api/devices/:id/command` | 控制未走统一指令通道 |

结论：OP 的设备控制**没有读 `/api/devices`**，与设备页是两套配置；驱动层从未注册真实驱动，所有卡片实际是「未配置驱动」的只读展示。必须收敛。

**收敛后 OP 的数据来源（全部可从设备表 + 快照运行态推导，不需要 OP 再存一份）**

| OP 需要 | 来源 |
|---|---|
| 显示哪些设备 | `GET /api/devices` → `devices`（按 type 分组） |
| 按席位显示 | `ownership.by_seat[seat]` + 天线所属树；席位列表来自现有 radioStates |
| 灯色三态 | `ownership.by_seat[seat].colors[antennaId]`（红/黄/绿） |
| 旋转器角度显示 | `rotators[id]`（physical / target / motion_state） |
| 旋转器指令 | `POST /api/devices/:id/command` `{command:"rotate",azimuth}` |
| 塔点动 | `tower_hold` 500ms 心跳 + `tower_release`，状态取 `towers[id]` |
| 切换器脉冲 | `select` + `config.channels` 推导可选端口/出口 |
| 发射状态 | `tx`（只显示，不进准入——互锁由服务端在指令入口执行） |

**设备表里没有对应字段、需要明确列出的缺口**

1. **席位 → 设备实例的显式绑定**：已由 `devices.seat` 解决（仅 `type='radio'` 生效）；OP 现在从设备表读取席位绑定的电台，多套同类设备不再靠 parent 链猜测。
2. **切换器可选端口/出口的清单**：`config.channels` 的键是 `port:outlet`，可反推，但没有独立的端口定义与显示名。
3. **设备口令输入**：设备有 `password` 时 OP 发指令需要口令，当前 OP 没有输入入口；需要增加一次性输入或会话内输入（前端 UX，不是数据缺口）。
4. **塔的限位/运动中状态**：已有 `towers[id].state`，无缺口。

**收敛改动（待 RF 链路问题裁决后一起实施，避免连做两次结构变更）**

- 删除 `deviceDefinitions` / `createPeripheralHub` / `renderAddMenu` / `configureDevice` 与三个 `op*Configured` 设置项；
- OP 增加设备快照轮询（复用 `public/shared/data/devices.mjs`），按席位渲染卡片；
- 指令统一走 `sendDeviceCommand`，与设备页共用租约、角度幂等、TX 互锁、审计；
- 地图点击转动改为向该席位对应的旋转器发 `rotate`；
- 未接入 TX 源时只显示「未接入发射状态源」，不放宽服务端互锁语义。

当前不改任何 OP 文件与 settings 结构，等用户对 RF 链路的裁决后再执行，避免返工。
