## 0. 先看这十条

1. **Node-RED 只是外壳**：`flow.json` 负责 UDP/MQTT/HTTP 接入、定时器、SQLite 节点和 WebSocket 广播；业务逻辑集中在 `lib/`，并且有架构测试强制「SQL 只能出现在 `lib/storage/`」「页面不能自己 `fetch`」。
2. **三个 SPOT 源 + 一个本台源**：dxwatch、RBN、PSKReporter 提供 SPOT；N1MM 提供本台电台状态、QSO、比分。HamAlert 只做过调研，**没有接入**。
3. **N1MM 三个 UDP 端口各管一类报文**：12060 `RadioInfo`、12061 `Contacts`、12062 `Score`；另有 `POST /api/n1mm/ingest` 供跨网段 relay 使用。`[代码]` `flow.json` UDP 节点、`lib/qsos/n1mm.js`
4. **席位是电台的属性，不是页面分区**：席位键由 N1MM 报文里的 ComputerName / StationName / RadioName / RadioNr 与来源 IP 推导，设备页全局组织，靠 `config.computer + config.model` 匹配到席位。`[代码]` `lib/qsos/seat-identity.js`、`lib/devices/ownership.js`
5. **设备画布是「统一节点 + 端口 + 连线」模型**：射频口方形、控制口圆形，端口 `in` 在下、`out` 在上；端口数量由型号定义派生，不手填。`[代码]` `lib/devices/rf.js`、`public/js/pages/devices-page.mjs`
6. **发射互锁只锁「天线切换」**：只对 `select` 生效，返回 423 `tx-active`；旋转器、功放、塔都不参与；没有二次确认放行。`[代码]` `lib/devices/commands.js:490-520`
7. **设备协议没有一条真机验收记录**：现有证据是厂商文档、构造报文/单元测试、厂商软件静态逆向、社区逆向四类混在一起。最危险的是把型号表里的 `verified:true` 当成「真机验证过」——它只表示协议表被人工核对过。详见第 4 章。

## 1. 项目定位与总体架构

### 1.1 它是什么

DX-Compass 是一个业余无线电竞赛态势感知系统：把公开 SPOT、本台 N1MM 状态、传播数据和站内射频设备状态汇总到同一张地图与同一组面板上，供比赛操作员判断「现在该在哪个波段、什么方向、有没有被占频、设备当前通到哪副天线」。

它不是日志软件，也不替代 N1MM：QSO 数据由 N1MM 单向广播进来，系统只读；设备控制是独立能力，和 N1MM 没有写回关系。`[代码]` `lib/qsos/n1mm.js`、`lib/devices/service.js`

### 1.2 运行时拓扑

```
浏览器 5758  ── HTTP / WebSocket ──┐
                                  ├─ Node-RED 3.x（flow.json + lib/）
浏览器 5859  ── bigscreen/server.js ┘        │
   只读代理，6 个 GET 接口 + 精确静态白名单   ├─ SQLite  dxcompass.db
                                             ├─ N1MM UDP 12060/12061/12062
                                             ├─ dxwatch / RBN  HTTP 轮询
                                             ├─ PSKReporter    MQTT 1883
                                             ├─ 传播源 HTTP（NOAA / HamQSL / KC2G / Open-Meteo / GIRO）
                                             └─ 站内设备 TCP / UDP / HTTP relay / MQTT
```

- 主进程：Node-RED，监听 `0.0.0.0:5758`。`[代码]` `settings.js:7-8`
- 大屏：独立 Node 进程 `bigscreen/server.js`，默认 `5859`，上游固定 `http://127.0.0.1:5758`。`[代码]` `bigscreen/server.js:29-31`
- 数据落盘：项目目录下 `dxcompass.db`；Node-RED 上下文目录 `.context/`。两者都在 `.gitignore` 里。`[文档]` README:563

## 2. 开发思路与技术路线

### 2.1 为什么是 Node-RED + `lib/`

- Node-RED 自带 UDP、MQTT、HTTP、WebSocket、定时器和 SQLite 节点，适合这种「多源、事件驱动、单机自用」的场景；不需要再写一套 HTTP/调度框架。`[代码]` `flow.json`
- 但把业务写进 function 节点会不可测。因此约定：**flow 只做适配，`lib/` 做领域逻辑**，并且测试会检查领域节点是否只是 `dx.*` 适配器。`[测试]` `tests/architecture.test.js:81`
- SQL 被强制收口在 `lib/storage/`，避免页面、解析器、flow 各自拼 SQL。`[测试]` `tests/architecture.test.js:73-78`
- 前端页面不能自己 `fetch`/`new WebSocket`，必须走 `public/shared/data/*` 仓库层；地图模块不能访问网络，数据模块不能碰 DOM。`[测试]` `tests/architecture.test.js:32-50`

这是一套「约束换可维护性」的结构：新功能如果绕过仓库层或存储层，测试会直接失败。

### 2.2 前端共享模块怎么组织

| 共享层 | 目录 | 复用方 | 解决什么问题 |
|---|---|---|---|
| 地图 | `public/shared/map/` | SPOT、QSO、传播、OP、大屏 | 底图、投影、图层、标记、晨昏线、边界、地表纹理只实现一份 |
| 地理 | `public/shared/geo/` | 地图、OP、分析 | 大圆距离/方位、网格、坐标 |
| 对手情报 | `public/shared/opponents/` | OP 页 + 5859 大屏 | 同一套卡片、颜色、形状、方位渲染，避免两边漂移 |
| 设置 schema | `public/shared/settings/schema.js` | 浏览器 + Node 服务端 | 唯一 schema 来源；服务端 `require` 同一个文件 |
| i18n | `public/js/i18n.js` + `public/js/i18n-gap.js` + `public/shared/core/i18n.mjs` | 所有页面 | 11 种语言；主词典 + 后补缺口词典合并，避免大文件冲突 |
| 传输/事件/时钟 | `public/shared/core/` | 所有页面 | WS 重连、事件总线、时钟对齐 |

### 2.3 RF 链路模型：统一节点 + 连线 + 端口方向

所有设备都是同一种节点，类型决定端口：

| 类型 | 射频端口 | 说明 |
|---|---|---|
| `radio` | `out` | 发射源 |
| `amp` / `tuner` / `notch` / `lna` / `balun` / `spd` / `coupler` / `swr` / `bpf` | `in` + `out` | 串联环节 |
| `antenna` / `dummy` | `in` | 终端 |
| `switch` | `in` + `ant1..antN` | 1×N |
| `matrix` | `in1..inN` + `out1..outN` | N×N |
| `combiner` | `in:<band>` ×N + `out` | 按波段合路 |
| `tower` / `rotator` | 无射频端口 | 只做控制/归属 |
| `serial` | 无射频端口 | 控制口 `net` + `serial1..serialN` |

`[代码]` `lib/devices/rf.js:88-152`

三条硬规则：

1. **一个射频口就是一根同轴接头**：已被占用时拒绝第二条连线，返回 409 `rf-port-busy`。`[代码]` `lib/devices/rf.js:387-397`
2. **RF 与控制彻底分开**：控制连线只允许「串口服务器 `serialN` ↔ 设备控制口」，不参与 TX 可达、波段剪枝、归属和互锁。`[代码]` `lib/devices/control.js:3-14,79-140`
3. **端口方向不可乱接**：进入必须是 `in`，离开必须是 `out`；`select` 还要求 `port.role === 'in'`、`outlet.role === 'out'`。`[代码]` `lib/devices/rf.js:193-199`、`lib/devices/commands.js:496-501`

### 2.4 端口怎么派生

- 切换器/矩阵的端口数由型号定义的 `defaults` / `port_count` / `in_count` / `out_count` 派生，不靠用户手填。`[代码]` `lib/devices/rf.js:110-129`、`lib/devices/model.js:338-350`
- 型号表声明 `in_count` / `out_count`（如 AG 8×2、ZSERVER 4×8、Green Heron 4×8）。`[代码]` `lib/devices/switch-models.js`
- 改型号或改端口数时，旧连线可能指向不存在的端口；批处理会重新校验并把悬空连线列为孤儿，而不是静默保留。`[代码]` `lib/devices/batch.js`、`lib/devices/rf.js:210-241`
- 最近一次提交就是把端口数从「手工字段」改成「型号派生」，这是当前 HEAD 的内容。`[提交]` `bb469bd`

### 2.5 可达判定

从电台（或任意起点）沿 TX 方向做 BFS：

- 起点：所有可离开的端口（`canLeave`）。
- 进入下游：必须是 `in` 侧；设备未启用、波段不匹配则剪枝。
- 合路器特例：进入端口带 `band` 时，必须与当前查询波段精确相等。`[代码]` `lib/devices/rf.js:318-319`
- 切换器/矩阵是「选择性导通」：已知选择只走选中的输出；未知选择且只有一个输出时视为唯一通路；多输出且未知时返回空（保守，不猜）。`[代码]` `lib/devices/rf.js:253-273`
- 到达 `antenna` 即记录路径；不重复计同一天线。`[代码]` `lib/devices/rf.js:321-326`

这套 BFS 是「当前波段下的理论可达」，不是机械位置回读。真正的开关状态由命令回读/遥测写入 `runtime.ports`，未知就是未知。

### 2.6 发射互锁怎么算

- 互锁只对 `select`（切换器/矩阵切天线）生效；旋转器 `rotate/stop`、功放 `amp_set`、塔 `hold/release` 都不做发射判定。`[代码]` `lib/devices/commands.js:490-520`、其余命令分支
- 取当前所有「已启用 + 健康 `ok` + `tx_active === true`」的 TX 源。`[代码]` `lib/devices/commands.js:253-258`
- 源绑定了设备时，按 RF 图从该设备反查会被影响的端口；只锁这条 TX 链路上的切换动作（`scope: 'path'`）。源未绑定设备时，退化为全局互锁（`scope: 'global'`）。`[代码]` `lib/devices/commands.js:274-290`
- 命中直接返回 423 `tx-active`，**没有二次确认参数，也没有「确认后放行」**。`[代码]` `lib/devices/commands.js:511-520`
- TX 源全部不可用时，按设计视为「未接入发射状态」，**不阻断、不沿用旧值、不把 unknown 当发射中**。`[代码]` `lib/devices/tx.js:1-11,46-54`

### 2.7 席位识别怎么做

一条 N1MM 报文进来后，按以下优先级得到 `seatKey`：

1. 来源带显式站点标识（`X-DX-Station` 或 query `station`）→ `STATION:<name>`，规则 `explicit`。
2. 有 `ComputerName` 或 `StationName`（`identityName = computerName || stationName`）→ 先用「ComputerName + RadioName + RadioNr」在注册表里找已存在的身份；找不到就新建 `CN:<计算机>|RN:<电台名>|NR:<序号>`，规则 `computer`。单机部署只有 StationName 时也走这一级。
3. 没有计算机标识但有来源 IP → `IP:<ip>|NR:<序号>`，规则 `source`。
4. 以上都没有：注册表只有一个实例时归到该实例（`single`），否则进 `UNIDENTIFIED`。另有一条 `NAME:<stationName>` 的旧兼容分支，但正常路径下会被第 2 级先接住。

`[代码]` `lib/qsos/seat-identity.js:243-296`

配套机制：

- 来源学习表会记住「IP:端口 → ComputerName / StationName / RadioName」，后续报文缺字段时补全。`[代码]` `lib/qsos/seat-identity.js:80-100`
- 手工 `rename / override / unbind / bind` 写回 `seatRegistry` 并留痕；手工结果在重连后继续使用。`[代码]` `lib/qsos/seat-identity.js:517-575`
- 席位心跳 = N1MM 上行；60 秒收不到就判离线，离线席位不再占天线，灯色回到绿。`[代码]` `lib/devices/ownership.js:20-60`
- 设备节点归属：`config.computer`（ComputerName 或 StationName）与 `config.model`（N1MM RadioName）同时匹配才算命中；两项都为空则显式未绑定，**不猜**。`[代码]` `lib/devices/ownership.js:70-89`

### 2.8 设置 schema

- 唯一来源：`public/shared/settings/schema.js`；服务端 `lib/settings/service.js` 直接 `require` 它。`[代码]` `lib/settings/service.js:3`
- 当前：**7 个域、135 个键、`SCHEMA_VERSION = 4`**（`ui` 12、`map` 19、`qso` 26、`wall` 18、`contest` 22、`data` 28、`prop` 10）。`[代码]` `public/shared/settings/schema.js:33,64`

- 配置档只存在浏览器，不写服务器。`[文档]` README:326

### 2.9 传播、建议与大屏复用

- 传播是「采集 + 缓存 + 近似模型」：NOAA/HamQSL/KC2G/Open-Meteo/GIRO 提供输入，`lib/propagation/model.js` 做估计。它不是 VOACAP，结果只能当趋势。`[代码]` `lib/propagation/`

## 4. 证据等级

这一章是交接时最容易被误读的部分。**请先记住：仓库里没有任何一条设备协议留下真机验收记录。** `docs/rf-component-spec.md:439` 对 ACOM 明确写了「本次环境不可达，未做真机抓包；所有帧样例均按解析器构造」。其它型号的取证边界也写在 §10–§17。若现场已经接过某台设备，请把记录补进本章，不要沿用本文的等级。

### 4.1 分级定义

| 等级 | 名称 | 判定标准 |
|---|---|---|
| L1 | 真机验证过 | 对真实设备抓包/操作，并有可复核的记录（时间、设备、帧、结果） |
| L2 | 模拟器/构造报文验过 | 单元测试、模拟器、手工构造帧；没有真机 |
| L3 | 依据厂商官方文档实现 | 有厂商手册/编程参考/协议文档；没有真机 |
| L4 | 从第三方软件逆向 | 厂商软件静态分析、社区项目、旧二进制、未公开 flow |
| L5 | 纯推测/未核对 | 没有可核对来源，或字段位置靠猜 |

> 数据源不是「设备协议」，L1「真机」不适用。表中给 dxwatch/RBN/PSKReporter 标 L2 + 现网，只表示「代码有测试、生产有流量，但没有契约/抓包证据」，不等于协议已被验证。

| 设备 | RemoteQTH Six2Two | L4 | topic 约定来自项目文档；`verified:false` |
| 设备 | Antenna Genius legacy 二进制 | L4 | 调研 flow 的旧帧，未在厂商文档核对 |
| 设备 | 干接点 relay（pulse/on/off） | L2 | 项目自定 HTTP 契约；有超时/脉宽测试；无真实继电器 |
| 设备 | 塔按住运行/限位 | L2 | 状态机测试；限位电平 NO/NC 取反有测试；无真机 |
| 设备 | TX 状态上报 | L2 | 项目自定 `source_id + tx_active`；健康度/降级有测试 |
| 设备 | 设备遥测 `device/report` | L2 | 项目自定；有构造报文测试 |
| 协议 | 官方设备 JSON 协议（A 档） | L5 | 自定 v1.0 + JSON Schema + 示例校验；**没有任何设备实现，服务端也没接** |
| 协议 | 平台内部 HTTP/WS API | L2 | 有契约测试；不是对外标准 |

### 4.3 分项说明

**数据源**

- dxwatch/RBN 是「网页在用的公开接口」，没有版本号、没有文档、没有 SLA；改版时只能靠现网报错发现。代码里有解析容错，但没有契约测试。
- PSKReporter 的 MQTT 主题是公开约定；订阅逻辑有测试，但 broker 的限流/断线行为没有长期记录。
- N1MM 的 XML 是事实标准。`tests/n1mm-parser.test.js` 用构造报文覆盖了字段缺失、单位混用、多实例；**没有真实 N1MM 报文样本**。

**设备**

- 型号表 `verified` 的语义必须澄清：它表示「协议表经过人工核对」，不是「真机验证」。`switch-models.js` 里 `verified:true` 的 AG/ZSERVER/Green Heron/wa4mcm 同样没有真机记录。`[代码]` `lib/devices/switch-models.js`、`[文档]` `docs/rf-component-spec.md:841-844`
- ACOM 的偏差是实质性的：官方 v1.1 要求 ACK，仓库不发 ACK，只靠「72 字节 + `0x55 0x2F` + 和校验为零」识别遥测；如果真机严格等 ACK，可能出现帧错位/动作不生效。`[文档]` `docs/rf-component-spec.md:283-289`
- OM Power 的证据是「厂商软件静态分析」，不是厂商协议文档；所有帧样例都是按解析器构造的，不是抓包。`[文档]` `docs/rf-component-spec.md:427-440`
- RF-Kit 只实现 `/info` 身份读取；功率/驻波/控制的端点不在官方手册里，明确不做。`[文档]` `docs/rf-component-spec.md:401-425`
- 官方 A 档协议是「为未来设备自定的规范」：字段一部分从现有实现反推，一部分是新定待评审；服务端只落了功放 MQTT，其余 5 类设备需要 G1–G10。`[文档]` `docs/third-party-device-onboarding-record.md:22-57`

### 4.4 最危险的三个误读

1. **把 `verified:true` 当成真机验证**。它只表示协议表已核对；界面上的「已验证」也应按这个语义理解。
2. **把官方 A 档文档当成已实现**。文档有 Schema、有示例，但服务端没有对应 driver，设备也没实现；现在接不上。
3. **把构造报文测试当成协议正确**。测试能证明解析器按预期工作，不能证明设备真的会发这些帧。

### 4.5 补证清单（接手后优先做）

| 优先级 | 要补的证据 | 方法 |
|---|---|---|
| P0 | 塔限位/方向/看门狗 | 现场用手动按钮 + 限位开关，记录每一路电平与动作 |
| P0 | 旋转器 GS-232 / rotctld | 抓 `C2;`、`Mxxx;`、`S;` 的真实回包，确认换行/静默分帧 |
| P0 | 切换器 AG / ZSERVER / Green Heron | 抓真实回读，确认 `verified` 状态转换 |

## 6. 已知未完成项与风险

### 6.1 硬件验收还没做的部分

**全部设备类都没有 L1 证据。** 具体包括：

- 塔：限位电平、NO/NC、方向通道、看门狗、断电行为
- 旋转器：GS-232 回包分帧、rotctld 连接、到位判定、换向前停止
- 切换器/矩阵：AG 双栈判定、ZSERVER 状态口、Green Heron 回读、RCS-4/Amplitec/Six2Two/Station Genius 的未验证帧
- 功放：ACOM 的 ACK 缺失、OM 的型号/功率缩放、KPA/SPE 的单位、RF-Kit 的 `/info`
- 干接点：脉宽、吸合、释放、断电保持
- N1MM：真实 12060/61/62 报文与多机场景

**结论：可以演示，不可以对外声称「已支持并已验证」。**

### 6.2 「能跑但依据不足」的地方

| 地方 | 现象 | 风险 |
|---|---|---|
| ACOM | 不发 ACK，只靠帧头和校验 | 真机可能不认，动作不生效或帧错位 |
| OM Power | 帧样例是构造的，型号表只放三型 | 真机固件差异可能导致功率/温度解析错 |
| Station Genius / RCS-4 / Amplitec / Six2Two | 帧/topic 来自逆向或推断 | 可能完全不通，或状态误报 |
| AG legacy | 旧二进制帧来自调研 flow | 新固件可能已不走该路径 |
| GS-232 | 回包可能不带换行，用 120 ms 静默分帧 | 慢速控制器可能被截断 |
| 塔 | 限位电平与方向由现场接线决定 | NO/NC 配错会把「已到位」判反 |
| TX 源 | 全部不可用时互锁放行 | 这是设计（O6），但现场要知道「没接 TX 源 = 不互锁」 |
| 席位识别 | 依赖 N1MM 字段与来源 IP | 换电脑名/双网卡会产生新席位 |
| 建议/告警 | 只在构造数据/单测里验证 | 没有实战胜负数据，规则阈值可能不适合现场 |

### 6.3 安全风险

- **没有认证**：`uiHost: 0.0.0.0`，`httpNodeCors.origin: "*"`，设备写接口只检查 `X-DX-Seat` 是否存在，不校验身份。`[代码]` `settings.js:7-8,46-50`、`lib/devices/commands.js:349`
- **明文存储**：QRZ 密码、设备 token、MQTT 密码、relay token 存在 Node-RED 上下文/SQLite 配置里，没有加密。`[代码]` `lib/settings/service.js`、`lib/devices/model.js`
- **无 TLS**：5758/5859 都是 HTTP；如果跨网访问，凭据和设备命令都可被嗅探。
- **CORS 头不含 `X-DX-Seat` / `X-DX-Operator`**：同源页面没问题，跨源客户端会在预检失败。`[代码]` `settings.js:46-50`
- **`/red` 已关**：这是好事；不要为了调试重新打开。

### 6.4 数据与协议风险

- dxwatch/RBN 是非官方接口，随时可能改版；没有契约测试，坏了只能看日志。
- PSKReporter 大区订阅的流量取决于全模式活动量；当前只按大网格收窄，数据库写入压力要关注。
- N1MM 的频率单位在不同版本/电台间可能不同；解析器做了启发式，但没有真机样本。
- 官方 A 档协议还在「待评审」：`proto`/`ts`/`device_class`/`boot_id`/`uptime_ms`、ack 帧、LWT、`fault_word` 位分配等都不是既成事实。`[文档]` `docs/third-party-device-onboarding-record.md:50-57`
- 文档与代码的 schema 计数已经漂移（104/6/cfgV3 → 135/7/cfgV4）。见第 9 章。

### 6.5 运行时风险

- **席位注册表、租约、设备运行态、频率协调都在 Node-RED global context**，不是 SQLite 事务。崩溃可能丢最近状态；重启后租约清空，设备状态要等回读/上报。
- **单进程假设**：租约是进程内 + context，两个 Node-RED 实例会各管一套，不能共享设备锁。
- **冷启动门闩只覆盖 HTTP/WS**：UDP 报文在 flows 启动前可能丢；N1MM 会周期重发，影响可接受，但要知道。
- **SQLite 单文件**：仓库没有配置 WAL，也没有备份策略；并发写靠 sqlite3 节点串行化。
- **`control_links` 启动探针缺口（已修复）**：原 `lib/storage/ready-sql.js` 只列 `rf_links` / `rf_links_pair`，但 `devices-sql.js:88,97` 会建 `control_links` 和唯一索引 `control_links_pair`；迁移失败时门闩会误放行。2026-11-17 已把表和索引加入探针，并在 `tests/architecture.test.js:309-321` 增加断言。`[代码]` `lib/storage/ready-sql.js`、`[测试]` `tests/architecture.test.js`

### 6.6 运维风险

- 没有自动备份/恢复脚本；`dxcompass.db` 是单点。
- 没有应用层日志文件，依赖 systemd journald 的全局轮转策略；长期运行仍要关注 `journalctl` 占用。
- `install.sh` 会改系统包、Node、服务，重复执行前要确认磁盘和端口。
- 生产版本可能落后；交接后第一件事应是核对 `git rev-parse --short HEAD`。

## 8. 踩过的坑与教训

### 8.1 冷启动 404 / 空白页

- **现象**：服务 `active`，端口也通了，但浏览器打开是 404 或接口空，几秒后才恢复。
- **根因**：Node-RED 先 `listen`，再异步启动 flows；端口刚开时 `http-in` 路由还没注册。数据库初始化也可能没结束，靠 `setTimeout` 猜不准。
- **解决**：`nodes/ready-gate.js` 在节点加载阶段挂全局中间件，等「schema 探针通过 + `flows:started`」两个条件同时满足再放行；WebSocket 的 `upgrade` 也先扣住，路由就绪后重新 emit。`[代码]` `nodes/ready-gate.js:1-96`
- **教训**：端口开 ≠ 服务就绪；健康检查要看 API，不要只看 `systemctl is-active`。

### 8.2 服务器手改文件导致 `git pull` 失败

- **现象**：生产拉取冲突，`git status` 有本地修改。
- **根因**：有人直接在服务器上改 `public/index.html`、`public/js/pages/qso-page.mjs`。
- **解决**：评审时先清理人工覆盖，再正常 pull；之后拉到 `856c6b3` 并重启。`[文档]` `docs/device-integration-review.md:27`
- **教训**：服务器只读；所有改动走本地提交。部署前先 `git status --short`。

### 8.3 两台 N1MM 实例互相覆盖

- **现象**：两个电台的状态/QSO 混在一起，席位错乱。
- **根因**：早期只用 `RadioNr` 做键，两台 N1MM 可能都用 R1。
- **解决**：引入席位键与 `n1mm_id` 命名空间；席位由 ComputerName/RadioName/RadioNr/来源 IP 推导。`[代码]` `lib/qsos/seat-identity.js`、`[提交]` `d7e371b`、`3e9d0d9`
- **教训**：`RadioNr` 只在单机内唯一，不是全局唯一。

### 8.4 ComputerName 与 StationName 不一致

- **现象**：换电脑名后席位识别不到，或旧部署只有 StationName。
- **根因**：N1MM 在不同配置下广播的字段不同；旧数据没有 ComputerName。
- **解决**：分级识别链 + 来源学习表 + 手工绑定；候选下拉不默认替用户选中。`[代码]` `lib/qsos/seat-identity.js:243-296`、`[提交]` `73788fd`
- **教训**：身份字段要「能学、能改、能显式未绑定」，不要猜。

### 8.5 频率单位混用

- **现象**：SPOT/QSO 频率差 10 倍或 1000 倍，波段判断错。
- **根因**：N1MM 的 `<Freq>` 可能是 Hz、10 Hz 或 kHz，取决于版本/电台。
- **解决**：`toKhz` 启发式归一，并用波段边界兜底。`[代码]` `lib/qsos/n1mm.js:46-51`
- **教训**：物理量入库前必须归一；不要相信字段名。

### 8.6 隐藏地图上的热力图重绘

- **现象**：切到其他视图后 JS 报错、CPU 飙高。
- **根因**：Leaflet 热力层在 `display:none` / 尺寸为 0 时仍被重绘。
- **解决**：尺寸为 0 或图层已移除时跳过重绘。`[提交]` `df796c2`、`a198b97`
- **教训**：地图类组件要处理「不可见」状态。

### 8.7 设置面板被地图盖住

- **现象**：打开设置，内容被地图 pane 挡住。
- **根因**：Leaflet 的 pane z-index 与页面层叠上下文冲突。
- **解决**：给 OP/设置视图建立独立层叠上下文。`[提交]` `00effe3`
- **教训**：地图页里的浮层要显式管理 `z-index`。

### 8.8 页面级设置抽屉被撤销

- **现象**：实现后要求撤回，设置入口回归设置页。
- **根因**：违反「设置入口不分散」的边界。
- **解决**：`f828713` revert；随后修了关闭按钮空目标报错 `3cd4d6f`。
- **教训**：这不是 bug，是设计边界；实现前先确认「入口放哪」。

### 8.9 切换器端口数变化留下悬空连线

- **现象**：改型号/端口数后，旧连线指向不存在的 `ant5`。
- **根因**：端口数曾经是手工字段，和型号能力不一致。
- **解决**：端口数由型号定义派生；批处理重新校验，悬空连线列为孤儿。`[提交]` `bb469bd`、`[代码]` `lib/devices/model.js:338-350`、`lib/devices/rf.js:210-241`
- **教训**：拓扑的端口集合必须是「派生值」，不能是自由文本。

### 8.10 SQLite 模式不是 RWC

- **现象**：数据库文件丢失后服务永久 `failed to open`，重启也没用。
- **根因**：`sqlitedb` 节点 mode 缺少 `CREATE`，不会自动建库。
- **解决**：`install.sh` 检查 mode 必须为 `RWC`，并用 sqlite3 预检建库。`[代码]` `install.sh:260-280`
- **教训**：部署脚本要检查「运行时真正依赖的配置」，不要只检查文件存在。

### 8.11 文件属主不一致 / dubious ownership

- **现象**：git 报 `detected dubious ownership`，或 Node 无法写目录。
- **根因**：历史 `chown` 与运行用户不一致。
- **解决**：`chown -R <run-user>:<run-group>`；`install.sh` 预检可写性并给出明确命令。`[代码]` `install.sh:95`
- **教训**：生产上「谁运行服务」和「谁拥有文件」必须一致。

### 8.12 功放「乐观置位」

- **现象**：点开机后界面立刻显示 ON，但设备没响应。
- **根因**：把「命令已发」当成「状态已变」。
- **解决**：下发后只写 `command_pending`，等回读确认；读不到就保持原值并标注未确认。`[文档]` `docs/rf-component-spec.md:770-771`
- **教训**：设备状态只能来自回读，不能来自命令。

### 8.13 把「从实现反推」的协议字段当成厂商标准

- **现象**：官方 A 档文档里混有「从现有实现反推」和「新定待评审」两类字段，容易被后来者当成既成事实。
- **根因**：协议是在已有功放 MQTT 实现上扩展的。
- **解决**：`docs/third-party-device-onboarding-record.md:50-57` 明确分成两类；新字段标注「待评审」。`[文档]`
- **教训**：协议文档要区分「事实」和「提案」；交接时不要把提案当契约。

### 8.14 Node-RED function 外部模块

- **现象**：想直接在 function 节点 `require` 第三方包，结果不可用或崩溃。
- **根因**：`functionExternalModules` 未启用。
- **解决**：继续关闭；共享逻辑放 `lib/`，通过 `functionGlobalContext` 暴露。`[代码]` `settings.js:29-37`
- **教训**：不要为了一个依赖打开外部模块，先把逻辑放进 `lib/`。

### 8.15 大屏白名单漏加模块

- **现象**：5758 正常，5859 某个模块 404，页面白屏。
- **根因**：大屏是独立进程，静态文件走精确白名单，不会自动跟随 `public/`。
- **解决**：新模块逐个加入 `bigscreen/server.js` 的 `STATIC` 并补测试。`[代码]` `bigscreen/server.js:50-92`、`[测试]` `tests/architecture.test.js:441`
- **教训**：大屏不是「另一个入口」，是一个独立的最小只读服务。
